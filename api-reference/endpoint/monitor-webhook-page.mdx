## When it's sent

One event for each page that, in a check:

- **changed** since the previous check,
- is **new**, meaning it appeared since the monitor's first check,
- was **removed**: it answers 404 or 410, or a complete crawl no longer finds it,
- or **started failing**. A page that stays down sends one event, not one per check.

Two things are never sent: the first check's baseline, where every page is new, and changes the [judge](/monitors/goals) ruled not meaningful. Both are still recorded on the check.

`data` is the same page object [`GET /monitor/{id}/checks/{checkId}`](/api-reference/endpoint/monitor-check) returns: status, diff, judgment and, in json mode, the current extraction.

## Responding

Answer with any `2xx` within **10 seconds**. A timeout, a `4xx` or `5xx`, or a redirect is retried after **1, 5 and 15 minutes**, then marked failed. Do slow work after you respond.

Retries carry the same `id`, also sent as `X-Prefetch-Delivery`. Store the ids you've handled and skip repeats.

## Verify the signature

Every request carries an `X-Prefetch-Signature` header, signed with the monitor's `webhook.secret`. See [Verify signatures](/concepts/webhooks#verify-signatures) for the scheme and code in Node.js and Python.

## Headers

| Header | Value |
|---|---|
| `X-Prefetch-Event` | `monitor.page` |
| `X-Prefetch-Delivery` | The delivery id, the same as `id` in the body |
| `X-Prefetch-Signature` | `t=<unix seconds>,v1=<hex HMAC-SHA256>` |
| `User-Agent` | `Prefetch-Webhooks/1.0` |

Any `headers` you set on the monitor's webhook are sent as well.
