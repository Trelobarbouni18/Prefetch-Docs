## Overview

Prefetch limits how many requests your API key can have **running at the same time**. Paid plans have no per-minute cap: as soon as one request finishes, the next can start.

| Plan | Concurrent requests | Requests per minute |
|---|---|---|
| Free | 1 | 30 |
| Starter | 10 | No limit |
| Pro | 50 | No limit |
| Growth | 150 | No limit |
| Scale | 500 | No limit |
| Enterprise | Custom | No limit |

Going over a limit returns HTTP `429 Too Many Requests`. A refused request costs no credits.

## Concurrency limit

Each key can have a fixed number of requests in flight at once. A request that would go over it is refused straight away with `429`, rather than queued:

```json
{
  "error": "Concurrency limit exceeded — too many requests in flight",
  "limit": 50
}
```

Every response that counts toward the limit carries two headers, so you can pace yourself:

| Header | Description |
|---|---|
| `X-Concurrency-Limit` | Maximum concurrent requests allowed for this key |
| `X-Concurrency-Running` | Number of requests currently in flight, including this one |

The simplest way to stay under it is a worker pool the size of your plan's limit. Each worker sends its next request when its last one finishes.

## Per-minute limit

The Free plan allows **30 requests per minute**, counted over a sliding 60-second window. Paid plans also carry a high per-minute safety ceiling that stops runaway loops; ordinary traffic does not reach it. Either one answers:

```json
{
  "error": "Rate limit exceeded",
  "retryAfterSeconds": 12
}
```

with a `Retry-After` header in seconds. Responses also carry `X-RateLimit-Limit` and `X-RateLimit-Remaining`.

## Requests without an API key

Requests that carry no API key or token are limited to 300 per minute per IP address. After 60 unknown API keys or invalid tokens from one IP address in a minute, that address is refused for the rest of the minute with `429` and a `Retry-After` header. Requests made with a valid key never count toward either limit.

## Handling 429 responses

When you receive a `429`, implement exponential backoff before retrying:

<CodeGroup>

```javascript Node.js
async function fetchWithRetry(url, options, maxRetries = 3) {
  for (let attempt = 0; attempt < maxRetries; attempt++) {
    const res = await fetch(url, options);

    if (res.status !== 429) {
      return res;
    }

    const backoffMs = Math.pow(2, attempt) * 1000; // 1s, 2s, 4s
    await new Promise((resolve) => setTimeout(resolve, backoffMs));
  }

  throw new Error("Max retries exceeded");
}
```

```python Python
import time
import requests

def fetch_with_retry(url, params, headers, max_retries=3):
    for attempt in range(max_retries):
        r = requests.get(url, params=params, headers=headers)

        if r.status_code != 429:
            return r

        backoff = 2 ** attempt  # 1s, 2s, 4s
        time.sleep(backoff)

    raise Exception("Max retries exceeded")
```

</CodeGroup>

## Tips for staying within limits

- **Batch wisely** — use `/enrich` instead of separate `/brand` + `/company` + `/classify` calls to reduce request count
- **Cache responses** — most brand/company data is stable; cache it for hours or days
- **Deduplicate** — avoid re-fetching the same domain multiple times in a short window
- **Match your concurrency** — for large jobs, run as many requests in parallel as your plan allows and no more; extra requests are refused, not queued
